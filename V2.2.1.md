# Lassi Shop POS — WindowsPOSV2 V2.2.2

## What this document describes

This is a technical and operational guide to the POS implementation in this WindowsPOSV2 repository. It describes the checked-out source, including its Electron desktop behavior and browser-development fallback; it does not imply that a Windows installer has been built or published.

The current `package.json` version is `2.2.2`. Generated `dist/` output, packaged release binaries, local `.env`, and runtime databases are not treated as source-of-truth implementation.

## Product overview

Lassi Shop POS is a single-store point-of-sale app for dine-in/table, parcel, takeaway, and delivery service. It is built with React and Vite and can run in a browser during development or as a desktop app through Electron. The desktop app uses SQLite for its catalog, tables, and orders, and supports silent printing, Excel report export, and optional order replication over the local network.

The main operational loop is:

1. Sign in.
2. Create an order from the catalog or open an occupied table.
3. Add items, item variations, quantities, order details, and notes.
4. Save the order, issue a KOT, print a cashier receipt, or hold the in-progress cart.
5. Reopen active orders, settle table orders, mark completed orders, and use the completed-order archive for lookup/reprints.

The interface defaults to dark mode, has a persistent light theme, and uses responsive React/Tailwind layouts. INR is used for displayed currency.

## Technology and runtime layout

| Layer | Implementation |
| --- | --- |
| UI | React 19, JavaScript/JSX, React Router 7, `react-icons` |
| Build and styles | Vite 8, Tailwind CSS 3, global CSS |
| Desktop shell | Electron 38 |
| Local database | SQLite via `better-sqlite3` |
| LAN transport | WebSocket via `ws` |
| Spreadsheet export | `xlsx` |
| Lint | Oxlint |

`src/main.jsx` mounts the app and hides the startup splash. `src/App.jsx` initializes the theme and, in Electron, loads orders from SQLite before routing. `HashRouter` supports the packaged `file://` app and the second database-viewer window. The main window loads `dist/index.html`.

The renderer calls privileged desktop features through `window.pflDesktop`, exposed by `electron/preload.cjs` with `contextBridge`. The bridge invokes `pfl:*` IPC handlers in `electron/main.cjs`; the main process owns windows, printer access, file access, export, the WebSocket host, and database calls into `electron/db-core.cjs`. Electron uses context isolation and disables renderer Node integration.

| `/customers` | CRM profiles, order history, and service notes | `role === "Admin"` or `role === "Manager"`; financial details are Admin-only |

Unauthenticated navigation redirects to `/Auth` and carries the requested route for return after sign-in. Restricted route checks use the current role, and Electron also verifies the authenticated role in the main process for privileged user, catalog, sync, report-export, and SQLite-viewer IPC operations.

### Role permissions

- **Admin:** Full application administration, all user management, all-order financial details/reprints, sales reporting, and SQLite viewer access.
- **Manager:** Add/edit/delete menu items, add categories, change their own password and passwords for Assistant Managers/Cashiers, and view completed orders without monetary values or receipt reprints. Manager permissions are role-wide because the user model does not associate staff with a specific manager.
- **Assistant Manager:** View completed-order history and non-financial customer profiles, maintain customer service notes, and change only their own password. They do not receive catalog/staff administration, sales-report, financial-detail, receipt-reprint, or SQLite-viewer access.
- **Cashier:** POS workflows; user, catalog, sales-report, and SQLite-viewer administration remains unavailable.
- CRM profiles are keyed by the normalized phone number on an order. Orders without a phone number are not merged into a customer profile.

The home header includes a global search over route labels, catalog item name/category/code, and users; results navigate to the route, prefill a sign-in username, or start a new order with a selected item. The profile menu displays the current user, toggles theme, and signs out. Authentication is held in `sessionStorage` until sign-out or the session ends.

## Staff workflows

### Create or edit an order

- Choose Table, Parcel, Takeaway, or Delivery.
- Browse categories or search item names. Favourites and Frequently Used stay pinned above the other categories. Frequently Used ranks products by quantity across completed orders and refreshes when orders change. Menu items marked vegetarian/non-vegetarian receive corresponding indicators.
- Items with variations prompt for a variation; each variation is a separate cart line. Repeated selections of the same item/variation increase quantity.
- Adjust quantity, add an item note, or add an order-level note.
- Table orders collect a table number. Parcel and Takeaway collect customer name and phone. Delivery collects phone and address.
- When a saved customer's 10-digit phone number is entered for Parcel, Takeaway, or Delivery, the POS fills any blank name and delivery address fields from the CRM. Staff can still edit the suggested details; changing the phone clears only values that were auto-filled and left unchanged.
- Parcel/Takeaway charges are capped at 10 by the entry handler. Delivery charges are entered separately. The displayed total is item subtotal plus the applicable charge; the composer does not add a tax or discount.
- Save stores the order without printing. KOT saves with `status: "kot"`; Save & Print saves with `status: "saved"` and prints a cashier bill; KOT & Print saves with `status: "kot"` and prints to the kitchen destination.
- The bill number is a three-digit local sequence (`001`, `002`, …); the token number is a separate daily sequence. The business date rolls over at 03:00 local time. Both sequences are stored in localStorage, not in the database.
- Reopening an existing order keeps its ID/order number. Changes are persisted as an updated order; when printing an edited order, the print action includes newly added or changed cart lines rather than automatically reprinting every unchanged line.

### Hold and resume

The Hold action saves the current cart in the `pfl-held-orders` localStorage key and clears the active composer. Held carts are local to that browser/profile and are not part of SQLite order persistence or LAN sync. They can be restored or discarded in the New Order drawer.

When closing the Electron POS, the app checks SQLite orders and locally held carts. If open orders or held carts exist—or order state cannot be verified—it offers Keep POS Open or Close Anyway. Closing does not settle, complete, or delete those orders.

If a new table order targets a table with an active order, the UI asks the operator to hold the new cart and navigate to the existing order's settlement flow instead of silently creating a second table order.

### Work tables

Tables combines configured table names with table numbers currently used by non-completed table orders. An active order marks its table occupied. From an occupied table, staff can view/reopen the order, print a kitchen KOT, or settle the bill. Settlement calculates displayed change from the amount received; it does not persist a payment/tender record. The order becomes completed either after a successful print-and-settle action or when settlement is completed without printing.

Tables can also be opened from New Order and carry navigation state to return to the previous screen.

### Process active and completed orders

Orders has Parcel/Takeaway, Deliveries, and Tables views. Non-completed orders remain in these active queues and can be reopened. The Completed button changes status to `completed`; it does not delete the record.

All Orders filters completed orders and supports searching order number, customer, phone, and table. Its detail dialog shows saved order items/details/totals and can reprint the cashier receipt for Admins. Managers and Assistant Managers can review order details without financial values or receipt reprints.

## Admin and setup tools

### Printer and bill layouts

Printer Settings assigns separate kitchen and cashier destinations. A destination can be an installed printer or a network printer IP/port. In Electron, an unset installed-printer destination falls back to the first available system printer. Desktop printer names can also be set with `PFL_KITCHEN_PRINTER` and `PFL_CASHIER_PRINTER`.

Bill Printing Preferences keeps separate selected template IDs for kitchen and cashier. Built-in layouts include the photo-style cashier receipt, Kitchen KOT 80mm, Classic, Minimal, and Customer details. Both built-in bills default to 80mm. The cashier layout follows the supplied receipt reference: centered logo and configured header phone, customer and address lines, date/type and cashier/bill metadata, item/quantity/unit-price/amount columns, quantity/subtotal/charges/grand-total rows, and configurable footer details. Table settlement's Save & Print uses this long cashier receipt and includes the table number. Admin/staff can create blank layouts, duplicate/delete layouts, set width (58/80mm), alignment, typography, spacing, divider, business/header/footer text, fields and field labels, field ordering, and dividers. The Kitchen KOT layout defaults to Verdana, 14px text, 16px title, an 80mm page, screenshot-derived spacing, a visible KOT number, centered date/type, dotted rules, customer/biller rows, and a compact item/quantity table. It has dedicated horizontal paper margin and extra bottom-feed controls; paper height remains content-driven because KOT item counts vary. The cashier receipt's left HTML margin is 3mm; larger text and longer item names wrap within the selected paper width and use content-driven height rather than being clipped. Network thermal printers use their built-in font; custom cashier logo output is rasterized for ESC/POS printers. PNG, JPEG, or WebP custom logos up to 500 KB are accepted. Template data is saved with printer settings on desktop and in browser localStorage in browser mode.

Electron printing is silent. Installed printers receive rendered HTML through a hidden print window; network printers receive ESC/POS data over TCP (default port 9100). Browser mode opens the browser print dialog and does not provide Electron silent-printer integration. Test the actual target printer, paper width, and template on the target OS; the browser preview alone does not verify physical output.

### LAN POS sync

An Admin can enable sync and select Host or Client in Network Sync. Desktop host mode starts a WebSocket server on all interfaces (default port `4099`) and is restored at app startup when enabled. A client connects to `ws://<host>:<port>` and creates a pending request. The host Admin must approve it; approval generates a cryptographically random connection token and delivers it to that client. The client stores the token for reconnection, and the host stores only its SHA-256 hash in `sync-clients.json`. Admins can reject requests, disconnect live clients, or revoke approved devices. Unapproved sockets receive no POS data and cannot submit changes. An approved client receives a full host snapshot; the host applies authorized client updates and broadcasts the resulting state to connected devices.

An authorized client receives and persists a host snapshot of the SQLite tables, menu, tables, orders, staff-account hashes, customer records, and shared receipt preferences/templates, including selected receipt-template IDs and cashier-to-kitchen routing. The selected physical cashier and kitchen printers remain local to each computer and are not synced. Client changes to orders, menu, tables, customer notes, and shared receipt preferences are queued in browser storage while offline and submitted after reconnecting. Order updates are merged by order ID and `updatedAt` so a stale offline snapshot does not discard other orders or replace a newer version; explicit deletions are sent separately. Same-order edits made concurrently can still conflict, and displayed bill-number sequences are local rather than centrally allocated.

The host's `users.json` keeps its existing account data; only derived scrypt password hashes are sent to clients. An Electron client can authenticate with the host's current staff credentials while offline after receiving a snapshot. Sync includes a full SQLite snapshot, so host and client builds must use compatible database schemas. Ensure host/client machines can reach the selected LAN address and port. The WebSocket transport is plain `ws://`, not TLS; use only on a trusted LAN or private VPN, and do not expose the port directly to the public Internet.

### Sales dashboard and export

Admin Settings calculates total revenue, order count, and average order value from all locally available stored orders. Its sales view shows period totals and recent sales. The report view includes daily, monthly, and yearly amount/order summaries, category quantity mix, and top-selling items.

The period buckets cover the last seven days, the last five months, and a year range including at least the current year and four prior years (extended for older/newer order data). The dashboard does not filter orders by completion status when summing these values.

Excel export is available only in Electron. The workbook contains an `Overview` sheet (total revenue, total orders, average order value) and a `Recent Orders` sheet (order number, creation time, type, table, status, total). A native save dialog chooses the `.xlsx` destination.

### Developer Mode

Admin Developer Mode can add/edit/delete menu items, set unique optional item codes, edit base prices, diet/favourite flags and variations, add categories, add/delete tables, add/edit/delete users, and reset bill numbering to `001` without clearing saved sales. Codes can still be used for keyboard item lookup when present. Configured accounts cannot be deleted. Managers receive catalog and password-only staff controls; Assistant Managers receive only their own password control. Passwords are not displayed in the user editor. User management is stored in desktop `users.json` in Electron or localStorage in browser mode.

### Customer CRM

The Customers page is available to Admins, Managers, and Assistant Managers. Orders with a phone number automatically create or update a customer profile keyed by its normalized digits. Profiles show customer contact details, completed-order count, last visit, searchable order history, and editable service notes. Admins can also view order amounts and lifetime spend; those financial fields are not returned to Manager or Assistant Manager CRM requests. In browser mode, profile data is derived from saved orders and notes are stored separately in localStorage. Customer contact information is sourced from order details; notes are maintained on the customer profile.

### SQLite viewer

The Admin-only viewer is desktop-only. It lists database tables, displays columns/rows, and supports inserting, editing, and deleting rows. Its privileged IPC reads and mutations are also restricted to an authenticated Admin in the Electron main process. It also calculates daily/monthly/yearly reports from stored orders. Direct database edits can bypass normal application workflows; use with care and maintain an external backup before changing production data.

## Data model and persistence

### Desktop

Electron stores app data under `<Electron appData>/Lassi Shop POS`; the SQLite file is `pfl.sqlite`. On startup, the app moves Electron `userData` to this shared app-data folder and copies a legacy `pfl.sqlite` only if the target database does not already exist. SQLite uses WAL journaling.

| Data | Desktop storage |
| --- | --- |
| Orders | SQLite `orders.payload` JSON snapshots; renderer hydrates `pfl-orders-v2` from SQLite |
| Catalog | SQLite `categories` and `items` |
| CRM profiles | SQLite `customers`, keyed by normalized phone number; order snapshots retain `customerId` |
| Tables | SQLite `tables` |
| Users | `users.json`, with configured accounts combined with local overrides; client snapshots contain derived password hashes |
| Printer/templates | `printer-settings.json` |
| LAN sync settings | `sync-settings.json` |
| Approved LAN sync clients | `sync-clients.json` (host stores token hashes only) |
| Theme, bill sequence, renderer cache | Browser localStorage |
| Authentication session | Browser sessionStorage |

The SQLite schema contains `categories`, `items`, `tables`, `users`, `orders`, `customers`, and `settings`. The users/settings tables exist, but the current user and printer/sync settings flows use JSON files instead. Each order row stores the serialized full order in `payload`; order shape is owned by renderer utilities and pages rather than normalized database columns.

On a newly created SQLite database, initialization seeds the catalog and default tables from `electron/menu-seed.cjs`. An existing database whose menu is intentionally emptied remains empty across restarts. The seed currently has 322 items, 26 categories (including All and Favourites), and 58 variations across 25 items. The checked-in `Menu.csv` is not read by the application runtime. In browser mode, the built-in fallback catalog in `src/utils/catalog.js` is a small 11-item sample; desktop seed contents are not automatically loaded into browser localStorage.

On first run of the Windows data-clean marker flow, existing orders are deleted once and the marker `.clean-sales-initialized` is written. Catalog data is not cleared by that operation. Be aware of this behavior when deploying or testing on a Windows machine with an existing user-data directory.

### Browser development

When `window.pflDesktop` is absent, localStorage adapters are used for orders, catalog/tables, users, printer settings, sync settings, and held orders. Browser storage is isolated from Electron's SQLite and JSON files. Browser-mode orders are therefore not automatically shared with the desktop database.

Key renderer storage names include:

| Key | Purpose |
| --- | --- |
| `pfl-orders-v2` | Saved order snapshot |
| `pfl-held-orders` | In-progress held carts |
| `pfl-bill-sequence-v2` | Daily local bill sequence |
| `pfl-catalog-v1`, `pfl-tables-v1` | Browser catalog and table fallback |
| `pfl-users-v1` | Browser editable users |
| `pfl-customer-notes-v1` | Browser CRM profile notes |
| `pfl-printer-settings-v1`, `pfl-sync-settings-v1` | Browser printer and sync preferences |
| `pfl-auth-user` | Current signed-in user in sessionStorage |
| `pfl-theme` | Dark/light theme |

Order updates write the renderer snapshot, request a SQLite write in Electron, push a sync snapshot when configured, and dispatch `pfl-orders-updated` for page refreshes. Orders now include a schema version and stable customer ID when a phone is entered. Delivery orders have a separate, versioned `deliveryDispatch` data object for future rider assignment/status integration; the current POS does not assign riders, expose rider APIs, or implement a delivery app. Startup hydrates desktop orders from SQLite. The Windows cleanup flow also clears the renderer order snapshot and bill counter on its one-time run.

## Order and receipt shape

An order is stored as a complete JavaScript object. The currently used fields include:

| Field | Meaning |
| --- | --- |
| `id`, `orderNumber` | Local order identifier and displayed bill number |
| `cart` | Item snapshots with product/line ID, name, category, price, quantity, optional variation and item note |
| `orderType` | `Table`, `Parcel`, `Takeaway`, `Delivery`, or fallback `Unassigned` |
| `orderDetails` | Table number, customer name, phone, and/or delivery address |
| `charges`, `subtotal`, `total` | Charge map and calculated amounts |
| `orderNote` | Instructions attached to the whole order |
| `status` | Operational state: commonly `saved`, `kot`, or `completed` |
| `destination`, `createdAt` | Last print destination (when applicable) and ISO timestamp |

Receipt templates can display customer/table/contact details, cashier, item prices, charges, discount, notes, totals, and footer. Receipt rendering escapes HTML text before inserting dynamic user/order strings.

## Configuration and distribution

Set local account values through `.env` using the variable names in `.env.example`: `VITE_CASHIER_NAME`, `VITE_CASHIER_USERNAME`, `VITE_CASHIER_PASSWORD`, `VITE_ADMIN_NAME`, `VITE_ADMIN_USERNAME`, and `VITE_ADMIN_PASSWORD`. Keep the real `.env` private; the Electron builder configuration includes `.env` as a packaged resource, so do not treat packaged client-side credentials as a secure authentication boundary.

Run commands from the WindowsPOSV2 repository root:

| Command | Effect |
| --- | --- |
| `npm run dev` | Start Vite browser development |
| `npm run build` | Build renderer assets into `dist/` |
| `npm run preview` | Preview the Vite build |
| `npm run desktop` | Build and launch Electron |
| `npm run db` | Build and launch Electron with `--db-viewer` argument |
| `npm run lint` | Run Oxlint |
| `npm run dist` | Build the branded Windows x64 NSIS installer under `release/` |
| `npm run desktop:win` | Build the unpacked Windows app and launch its executable (run on Windows) |

The GitHub Actions workflow `.github/workflows/windows-build.yml` uses Node 20 on `windows-latest`, installs npm dependencies, builds the Vite app, packages and verifies an unpacked app, then uploads the NSIS installer as `lassi-shop-pos-windows-installer`. The dedicated app-icon source is `build/app-icon.png`; Windows uses `build/icon.ico`. The in-app branding image `public/Logo.png` is independent. On first account access, the app creates `%APPDATA%\Lassi Shop POS\users.json` from configured accounts if that file does not exist. There is no test script configured in the current package manifest.

## Known boundaries to keep in mind

- Desktop SQLite is the durable source for desktop orders; browser localStorage is a separate development fallback.
- LAN sync uses plain WebSockets and is not end-to-end encrypted; use a trusted network/private VPN, never a public port-forward.
- Offline queues and order `updatedAt` merging reduce data loss, but simultaneous edits to the same order and globally unique bill numbering are not coordinated.
- Bill numbering is localStorage-backed and not a database-enforced unique ID. Multiple independent clients can generate the same displayed number.
- Settlement computes change for display but does not store payment amount, payment method, or tender history.
- Sales summaries currently count the locally stored order list without filtering to completed orders.
- Printing, Electron userData behavior, network printers, report export, and packaged asset paths require desktop/target-OS testing; browser testing does not validate them.
- SQLite viewer edits can change records outside the normal UI and should be treated as direct production-data operations.
- Generated binaries, `dist/`, local databases, `.env`, and real credentials are local/release data, not source documentation inputs.

## Verification checklist

Use the existing project commands:

```sh
npm run lint
npm run build
```

For a desktop release or a change involving desktop-only features, also verify on the target OS:

- sign-in, redirects, and Admin-only route behavior;
- order creation, variations, item/order notes, charges, hold/resume, and reopen/edit flows;
- table occupancy, table collision handling, settlement/change, and completion;
